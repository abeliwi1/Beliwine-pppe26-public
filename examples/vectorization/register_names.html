Thirty-Two Names for Sixteen Registers

A register is a place, not a name. The same storage answers to rax, eax, ax, al — and on the vector side, to zmm0, ymm0, xmm0.

General-purpose registers

Sixteen of them. Each holds 64 bits, and the narrower names address the low end of the same storage — writing eax writes the low half of rax.

any ISA level legacy high-byte name, only on the first four no name at this width

Vector registers

Thirty-two of them on this part. xmm is the low 128 bits of ymm, which is the low 256 of zmm — one place, three names.

reachable by SSE, VEX and EVEX EVEX only — AVX-512 adds these not reachable at the selected level

Mask registers

Eight, and entirely new with AVX-512 — they have no name under SSE or AVX2. Each holds one bit per lane, so an instruction can write some lanes and leave others untouched.

k0 is readable and writable like the others, but naming it as an instruction's write-mask means no masking — there is no way to spell "mask with k0".

What is shared and what is not

Registers 0–15 are shared ground: an SSE instruction, a VEX-encoded AVX2 instruction, and an EVEX-encoded AVX-512 instruction can all name the same physical register, just at different widths.

Registers 16–31 are not reachable at all without EVEX encoding. They exist on this chip, and because it has avx512vl they can be addressed at 128 and 256 bits as well — but only by an EVEX instruction. There is no way to write xmm20 in an SSE or AVX2 instruction, because those encodings have nowhere to put the extra register number.

So AVX-512 on this part is not only wider registers. It is twice as many of them, plus eight mask registers — which is why it helps code that was short of registers even when the vectors stay 256 bits wide.

One important asymmetry

Writing a narrow view does not always leave the rest of the register alone.

what you writewhat happens to the upper bits
eaxzeroed — writing a 32-bit GP name clears bits 32–63
ax, alpreserved — the rest of rax survives
xmm0, SSE encodingpreserved — bits 128 and up are left as they were
xmm0, VEX or EVEX encodingzeroed — bits 128 and up are cleared

That last pair is the reason for vzeroupper: mixing legacy SSE writes with VEX code leaves the upper halves in a state the hardware has to reconcile, and on some parts it costs a stall on every transition.
