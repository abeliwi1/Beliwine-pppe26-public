Before the Autopsy

A short grounding in Java threads and ForkJoinPool — what a thread actually costs, why fork/join exists, and how work-stealing moves tasks between threads — before watching one fall apart under measurement.

A thread is not free

A java.lang.Thread isn't a language-level abstraction the JVM simulates — it's a thin wrapper around a real operating-system thread. Creating one means the OS allocates a stack (megabyte-ish by default), sets up scheduling state, and hands back a kernel handle. None of that is instant, and none of it is free: spin up a thousand threads for a thousand tiny tasks and you can spend more time creating and context-switching between them than doing the work itself.

That single fact drives almost everything else in this primer — and, as it turns out, the autopsy that follows it.

From one thread to a pool

The obvious fix is to stop creating threads per task and reuse a fixed set of them instead — a thread pool. An ExecutorService is the general-purpose version: submit a Runnable or Callable, a worker picks it up from a shared queue, and you collect the result later via a Future. This works well when tasks are independent and roughly uniform — handling web requests, resizing a batch of images, running a fixed list of queries.

It works less well for a specific shape of problem: recursive divide-and-conquer, where a task doesn't know how many subtasks it needs until it's already running, and a "task" is often just recursing one level deeper and waiting on itself.

Why divide-and-conquer needs its own pool

Imagine submitting each half of a recursive sum to a plain ExecutorService and blocking on Future.get() to combine them. With a bounded pool, that's a trap: a worker thread can end up blocked waiting on a subtask that's still sitting in the queue behind other blocked workers — nobody is free to actually run it. Deep enough recursion, and every worker is waiting on work no worker is available to do.

ForkJoinPool exists specifically to make that pattern safe and fast: a task that's waiting can go help run other queued work instead of just blocking, and the whole pool is built around cheaply creating far more tasks than there are threads to run them.

How it actually schedules work

Each worker thread in a ForkJoinPool owns its own double-ended queue of tasks — not one shared queue. That's the whole trick:

  • fork() pushes a new task onto the calling thread's own deque, at its own end. Cheap and uncontended — nobody else is touching that end.
  • A worker pops its own next task from that same end (LIFO) — the most recently created task, which is also the most cache-hot one.
  • When a worker runs out of its own work, it becomes a thief: it reaches into another worker's deque from the opposite end (FIFO), taking the oldest, typically largest task there. Stealing the far end means thieves rarely collide with the owner working its own end.
  • join() doesn't just block. If the awaited task hasn't run yet, the joining thread can go execute other queued tasks while it waits — turning idle time into useful work instead of a parked thread.

The pool itself: shared, or yours

ForkJoinPool.commonPool() is a single JVM-wide instance, created lazily the first time anything asks for it — parallel streams, CompletableFuture, and any code that calls commonPool() all share it. Its size is fixed once, from Runtime.availableProcessors() - 1 (or a system property set at JVM startup); nothing resizes it while the JVM is running.

A pool you construct yourself with new ForkJoinPool(n) runs on exactly the same work-stealing engine — same deques, same fork()/join()/steal mechanics — but with a size and a lifecycle you control.

That distinction is the hinge the next piece turns on: a pool you construct yourself has an observable moment where it comes into existence, and a genuinely cold first invoke() where its worker threads actually get created. The common pool, shared and already warm, hides both.
