The ForkJoinSum Autopsy

A recursive fork/join sum looked like it should scale cleanly with thread count. It didn't. Chasing the gap between measured and ideal speedup turns up two separate serial costs hiding inside one Amdahl fit — and one of them gets worse the more threads you ask for.

N = 50,000,000 longs runtime OpenJDK 26 cores Apple silicon, 4P + 6E threshold 10,000 (leaf task size)

ForkJoinSum sums an array by recursively halving the range. Each half becomes a task; one half is handed off with fork(), the other is computed inline, and the two results are combined at join(). Below THRESHOLD elements, a task just adds sequentially — that's the base case every leaf of the recursion bottoms out on.

protected Long compute() { if (hi - lo <= THRESHOLD) { long sum = 0; for (int i = lo; i < hi; i++) sum += a[i]; return sum; // leaf: pure serial work } int mid = (lo + hi) / 2; ForkJoinSum left = new ForkJoinSum(a, lo, mid); ForkJoinSum right = new ForkJoinSum(a, mid, hi); left.fork(); // hand the left half to another thread long rightSum = right.compute(); // this thread keeps the right half long leftSum = left.join(); // wait for the left half return leftSum + rightSum; }

The baseline: measured speedup vs. Amdahl's law

Timed as steady state — the pool already warm, threads already alive, JIT already compiled — across 1–10 threads (80 repeats each, medians plotted). Fitting Amdahl's law, S(p) = 1 / (f + (1−f)/p), to the measured curve gives a serial fraction f ≈ 21.4%.

That's 2.7 ms of every 12.65 ms run that no thread count can ever remove — the textbook Amdahl ceiling, about 4.7× no matter how many cores you throw at it.

A cold run tells a different story

That 21.4% is measured after a warm-up call — it excludes pool construction and the first, cold invoke(), where ForkJoinPool actually spins up its worker threads. Include that first call, and the picture changes: pool construction is a flat ~0.28 ms regardless of pool size, but the first invoke gets more expensive as you request more threads — more OS threads to create before the first task can even run.

Stacking the three components of a real, one-shot invocation shows why: the Amdahl-serial term (aqua) stays fixed, the parallelizable work (blue) shrinks as expected — but startup overhead (orange) grows with thread count, and by 10 threads it dwarfs everything else in the bar.

Splitting the 2.7 ms itself

The Amdahl-serial term isn't one thing either. THRESHOLD controls leaf-task size — smaller leaves mean more fork/join pairs on the critical path. Sweeping it while holding N fixed and refitting Amdahl's law at each setting separates the two:

Coarsening from 5,000 leaf tasks down to 50 cuts the serial term from 2.6 ms to 2.1 ms, then flattens into a floor that finer or coarser granularity can't touch. With only 50 tasks, bookkeeping is microseconds — the floor is something else: most likely the external-thread wait in pool.invoke(), since the calling thread isn't a pool worker and has to park, then be woken once the root task completes.

What "serial" was actually made of

The classic Amdahl serial fraction (21.4%, 2.7 ms) is real but small, and most of it isn't even algorithmic. Roughly 0.5 ms scales with task count — fork/join bookkeeping on the critical path. The remaining ~2.1 ms is a fixed floor, most likely the external-thread handoff in pool.invoke(), unmoved by granularity.

None of that is where the real cost lives. A cold, one-shot run's non-scaling time is 74–93% thread-pool startup — and that portion grows with the very thread count you'd add for more speedup. For a short-lived computation, requesting more parallelism can spend more on creating the workers than it saves on the work itself.
