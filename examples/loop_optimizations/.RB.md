## The two traps that invalidated everything (both now fixed in all five files)

**1. Heterogeneous cores.** cpu0-3 are Zen 5 at 5.13 GHz; cpu4-11 are Zen 5c at
3.17 GHz.  An unpinned run lands wherever the scheduler puts it — a 1.6x spread
on the same binary.  All five now `sched_setaffinity` to cpu0.

**2. The governor never boosts a memory-bound loop, and min-of-N does not save
you.**  `amd-pstate-epp` (powersave / balance_performance) raises the clock in
response to **IPC**, not to the core being busy.  A memory-bound loop has low
IPC, so the core sits at ~3.59 GHz for the entire run — *every* repetition is
equally slow, so taking the minimum of five changes nothing.  Measured on the
transpose: **263 ms on all 8 repetitions cold, 184 ms on all 8 after a warm-up
spin.**  A stable, reproducible, 1.43x-wrong number.

The subtlety that cost the most time here: the obvious warm-up — spinning on
the same dependent ADD chain used to measure the clock — **does not work**.
That loop is itself low-IPC (~1.25) and the core stays at 3.57 GHz through 12
consecutive calls.  The warm-up has to be *eight independent* chains (~8 IPC).
All five files now do that and print the measured clock before and after the
run, so a drifting clock is visible rather than silent.

This trap invalidates the previous pass's M5 numbers too, since that harness
had no warm-up either.  Do not compare any M5 figure in the `.md` files
against anything here.

## What changed in the write-ups (all applied)

1. **`loop_unrolling.md`: the example does not demonstrate unrolling.**  On this
   machine 4× unrolling is worth 1.01–1.02x at *every* working set from 8 KB to
   64 MB, and Duff's Device is consistently ~5% **slower**.  The scalar loop runs
   at 1.0 cycles/element — the latency of the dependent chain through the
   accumulator — so loop control is already free and unrolling has nothing to
   remove.  Four independent accumulators give 1.65x, and at `-O2` the unrolled
   forms get vectorised (2.0x) while the scalar loop does not (checked with
   `-fopt-info-vec`).  The honest framing, now in the source: **unrolling is an
   enabler, not a win** — it makes room for ILP or for the vectoriser.

2. **`loop_tiling.md`: the optimum is B=16 at 5.5x** (M5 said B=8 at 2.96x; the
   previous pass said B=4).  Neither textbook rule picks it: capacity says
   B ≤ 55 and is badly wrong (B=48 and B=64 are near the bottom), associativity
   says B ≤ 12 and is at least in the neighbourhood.  The curve is not smooth —
   B=10 is reproducibly worse than B=8, because 8 doubles is exactly one 64-byte
   line and 10 straddles two.

3. **`loop_tiling.md`: tile size is the wrong variable.**  What governs the whole
   effect is the leading dimension.  `sets_reachable = 64 / gcd((lda/8) % 64, 64)`;
   at lda=4096 that is **1**, so an entire column fights over one 12-way set.
   Padding to 4104 makes the naive transpose **7.9x** faster with no tiling at
   all — and 1.4x faster than the best tile size ever reaches on the unpadded
   array.  The threshold is 16 reachable sets, which is the same number
   `set_conflict.c` in `../memory_hierarchy/` finds with a different kernel.
   Both tables are now in `loop_tiling.cpp`.

4. **`loop_tiling.md`: "avoid powers of two" is not the rule.**  lda=4352 is not a
   power of two and is still 3.1x off the best; lda=4097 is odd, drifts across
   sets, and performs like the well-padded cases.  The rule is how many factors
   of two the row length contains *measured in cache lines*.  The old B=80 bump
   was an M5 artifact and does not exist here.

5. **`loop_interchange.md`: the working-set argument is still wrong, differently.**
   Old text: "one row of A = 32 KB, x = 32 KB, total 64 KB = L1, exact fit."  L1d
   here is 48 KB, so 64 KB would not fit at all — yet the optimisation works fine
   (6.29x).  The row does not need to be retained; only `x` does, and 32 KB
   against 48 KB is a comfortable fit.  Also **8 doubles per 64-byte line**, not 16.

6. **`loop_fission.md`: the split factor is wrong for this ISA.**  The documented
   2×16 split leaves 57 stack references and most of the win unclaimed; **4×8
   reaches zero spills and 4.28x**.  x86-64 has 16 XMM registers where ARM64 has
   32, so the slice has to be half as wide.  Over-splitting to 8×4 removes nothing
   further.  The best fission factor is an ISA property and does not port.
   (Superseded once more by the local-accumulator fix below, which is what moved
   the headline from 2.2x to 4.28x.)

7. **`loop_fission.md`: the absolutes discrepancy is explained.**  The `.md`
   documents 202/90 ms; that is the **16-reference** version of the example.  The
   source has `REFS = 32` and its header comment still said 16.  Not measurement
   drift — a stale source comment plus a stale write-up.  Header now fixed.

## Open / not chased

* **Why B=16 and not B=12.**  The associativity bound predicts 12 and the measured
  peak is 16.  Presented as empirical rather than explained, which is honest but
  unsatisfying.
* **Huge pages make the unpadded transpose ~2x worse** (184 → ~355 ms).  Consistent
  with 2 MB pages making physical addresses as congruent as virtual ones, but not
  verified with counters — `perf` is not installed on this box.
* **Allocation congruence in `loop_fission`.**  32 same-sized `malloc`s come back
  identically aligned; staggering them by a cache line each is worth a large
  fraction of the 1-loop time, unrelated to fission.  Measured at 479 → 296 ms
  against the pre-fix kernel shape and not re-measured since the local-accumulator
  rewrite, so treat the effect as established and the number as stale.  Noted in
  the source; the benchmark still uses the natural allocation.

## Also found while writing the write-ups

**`loop_fission` was not demonstrating what it claimed.**  Accumulating into the
`c[]` output array meant GCC could not prove `c[k]` did not alias `ref[j][i]`,
so it reloaded the pointer and the accumulator from memory every iteration and
never put them in registers.  Result: a slow loop with **zero** spills — the
wrong mechanism entirely.  Switching to local accumulators makes the spills
real and measurable, and the speedup now tracks the spill count exactly
(134 → 57 → 0 stack refs against 1.00x → 2.59x → 4.28x).  The headline moved
from 2.2x to **4.28x**.

**`loop_fusion` documented a Welford's comparison the source no longer
contained.**  Restored as a third variant and re-measured: 192 ms, 0.31x.

**`PIN_CPU` override added** to all five, because cpu0 is not always free.
Defaults to cpu0; the banner reports the core it actually landed on.

## Correction, after re-examination (2026-09-22)

RB pushed back that tiling ought to matter and that set conflicts look like a
separate issue.  Both correct; the previous conclusion was over-generalised from
a kernel that cannot show what tiling is for.

**Tiling pays in proportion to reuse.**  Transpose is N^2 work on N^2 data --
reuse factor 1, every element read exactly once -- so a tile has no reuse to
capture and only spatial locality is on the table, which padding fixes more
cheaply.  Matrix multiply is N^3 on N^2, reuse factor N, and there blocking cuts
memory traffic by the tile size.  Measured, i,k,j baseline, -O3, T=256:

    n=512  (6 MB, fits L3)   27.2 -> 34.5 GF/s   1.27x
    n=1024 (24 MB)           26.5 -> 31.9 GF/s   1.20x
    n=2048 (96 MB)           10.7 -> 31.8 GF/s   2.98x

The blocked kernel holds ~32 GF/s at every size; the unblocked one collapses
once the matrices pass L3.  The win grows with the problem.

**They are independent.**  Padding helps the blocked version at small tiles and
does nothing for the unblocked one; blocking wins ~3x either way.

**Why it was missed the first time, twice.**  The inner loop is c[j] += a*b[j].
It needs __restrict (or the compiler cannot rule out aliasing) and -O3 (gcc's
-O2 uses the very-cheap vectoriser cost model and refuses it).  Without both,
every version runs scalar at ~1.3 flops/cycle, the kernel is memory-bound, and
blocking measures within 4% of not blocking.  Measured on the new source at
n=2048: -O2 says tiling is worthless, -O3 says 2.98x, same code.  The original
"tiled never beat the reordered baseline" note almost certainly hit this.

Also measured and rejected as simpler candidates: a 5-point stencil shows
nothing even at 64K-wide rows (reuse factor 4, one row of reuse distance --
the prefetcher has it), and all-pairs accumulation is worse (0.13x), because
N^2 work on N data means the array is tiny whenever the work is runnable.
Matmul's N^3/N^2 is the only common shape where the data can exceed cache while
the work stays tractable.

Added matmul_tiling.cpp / .md.  loop_tiling.md, README.loops.md and lecture 06
recast: transpose is now explicitly the no-reuse case and its "pad first" rule
carries that qualifier.
