What the strips are

The cells along the top and left edges are the data, not the iteration space. Point (i, j) reads one row operand and one column operand — in a matrix multiply, a row of A and a column of B. A strip cell lights amber while its operand is still needed by the work in flight.

Both walks light exactly one grid cell at a time. Count the amber instead.

The counters reset at each unit of work — one row sweep on the left, one tile on the right — and climb as that unit proceeds. Watch where each one tops out: the left panel reaches sixteen live columns, the right panel never passes four.

Why the counts differ

The unblocked walk finishes a whole row of j before moving to the next i. By the time it comes back to j=0, it has swept all sixteen columns — so every column operand has to have survived, or be fetched again.

The blocked walk stays inside a 4×4 tile. It needs four rows and four columns, and it reuses each of them four times before moving on.

At this size the saving is about half. The shape of it is what matters: unblocked needs 1 + N operands live, blocked needs 2B. Those scale completely differently — at N = 4096 with B = 64 that is 4097 against 128, which is the difference between missing cache on every pass and fitting comfortably inside it.

That is the whole of loop tiling: the iteration space is reordered so the working set stops growing with the problem.

Companion to examples/loop_optimizations/matmul_tiling.md, where blocking a 2048×2048 matrix multiply is measured at 2.98× over the best unblocked loop order. Note that tiling only pays when there is reuse to capture — a transpose reads each element once, and there padding the leading dimension beats it.
