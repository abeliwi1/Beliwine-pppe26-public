algorithm design · clang's libc++ introsort, measured on Apple M5

What libc++
Adds

clang's std::sort has the same three techniques as GCC's — a cutoff to insertion sort, a quicksort middle, a heapsort safety net — and on random int data it is 3× faster at a million elements. Almost all of that comes from one change in the middle: a partition that never branches on the data.

Three Techniques of std::sort takes GCC's libstdc++ apart and finds that, above the leaf, it costs exactly what plain quicksort costs: the same Hoare partition, the same number of times. libc++ keeps the skeleton and changes what happens inside it. Read from its source (__algorithm/sort.h, Apple clang 17):

The branch-free paths — the bitset partition and the 3/4/5-element networks — are meant for arithmetic types with a comparison libc++ knows has no branch of its own, such as the default operator<. On macOS the bitset partition actually reaches a program only through the copies of std::sort precompiled into the system library; the control below explains why.

1

the middle

A Partition That Never Mispredicts

A Hoare partition runs loops like while (a[++i] < pivot) {}. Every comparison decides whether the loop continues, and with a median pivot on random data each element is about as likely to belong on either side — so the branch predictor guesses wrong about half the time, and every wrong guess throws away work the core had already started.

libc++'s bitset partition (the BlockQuicksort scheme of Edelkamp and Weiß) makes the same comparisons and never branches on one. It works in blocks of 64 elements from each end: 

// 1. left block: which of these 64 belong on the right?
for (int j = 0; j < 64; j++)
    left_bits  |= uint64_t(!(a[first + j] < pivot)) << j;

// 2. right block: which of these 64 belong on the left?
for (int j = 0; j < 64; j++)
    right_bits |= uint64_t(a[last - j] < pivot) << j;

// 3. swap misplaced pairs, lowest set bit of each word first
while (left_bits && right_bits) {
    swap(a[first + ctz(left_bits)], a[last - ctz(right_bits)]);
    left_bits  &= left_bits - 1;     // clear lowest set bit
    right_bits &= right_bits - 1;
}
// 4. a block whose word reached zero is done: move that edge 64 inward

The comparison becomes a 0 or 1 shifted into a word; the loop always runs 64 times. The only data-dependent branch left is whether a word is empty, which depends on how many elements are misplaced, not on any one of them, and predicts well. It does more work than Hoare — every element is compared and recorded, even ones already on the right side — and it trades that for a straight run of work with nothing to mispredict.

The control: switch the partition off

Measuring the partition needs a std::sort with only the partition changed, and two facts about libc++ on macOS decide how to get one. First, std::sort on int is not compiled into your program at all: libc++ declares it an extern template, and the call goes to a copy precompiled into the system's libc++.1.dylib, which uses the bitset partition. Second, a sort compiled from this SDK's headers never uses the bitset partition, even with a comparator libc++ lists as branch-free such as std::greater: the header's dispatch checks the comparator without the & that list expects.

So sort_compare_large.cpp calls libc++'s own __introsort directly from the header, with the bitset-partition flag forced on and off. The cutoff at 24, the pivot choice, the 3/4/5-element networks and the heapsort fallback are the same code in both, so the ratio is the partition alone:

With the flag on, the header build matches the library copy to within a few percent, so how the library was compiled adds nothing. With it off, libc++ runs within 1–8% of libstdc++ at every size from 1,024 up — its later cutoff, per-partition insertion sort, small networks and better pivot add almost nothing on top of GCC's textbook introsort. The partition makes it 1.91× faster at a thousand elements and 2.88× at a million. The gain grows with n for the same reason the leaves shrink: the taller the tree, the larger the share of the work that is partitioning.

2

the leaf

A Later Cutoff, No Final Pass

libc++ stops partitioning below 24 elements rather than 16, and finishes each small range with insertion sort right there, instead of leaving it for one pass over the whole array at the end. Ranges of exactly 3, 4 or 5 elements get a fixed, branch-free sorting network instead.

At n = 16 both libraries are simply an insertion sort, and they cost the same: 0.99 ns per n·log₂n for libc++, 1.04 for libstdc++, against 1.94 and 2.09 for plain quicksort built with each compiler. The leaf is not where libc++ pulls ahead. A branch-free sorting network can beat both by a wide margin — see small_sorting.md, where a NEON bitonic network sorts 16 elements 6.8× faster than std::sort.

the tiny partitions

Sorting Networks for 3, 4 and 5

When a partition has exactly 3, 4 or 5 elements, libc++ skips insertion sort and runs a fixed sorting network: a sequence of compare-exchanges whose order never depends on the data. The same routines handle the whole array when std::sort is called on 3 to 5 elements. Like the bitset partition, they are used only for arithmetic types with the default comparison.

The building block is __cond_swap: compare two elements and leave the smaller in the first position. It is written with conditional expressions rather than an if, so the compiler can turn it into selects instead of a branch. The four-element network is five of them: 

// ensures *x <= *y, swapping if necessary (libc++ __cond_swap)
template <class Compare, class It>
void __cond_swap(It x, It y, Compare c) {
    bool r   = c(*x, *y);
    auto tmp = r ? *x : *y;      // the smaller
    *y       = r ? *y : *x;      // the larger
    *x       = tmp;
}

// libc++ __sort4_maybe_branchless
__cond_swap(x1, x3, c);   // layer 1: two independent pairs
__cond_swap(x2, x4, c);
__cond_swap(x1, x2, c);   // layer 2: smallest and largest settle
__cond_swap(x3, x4, c);
__cond_swap(x2, x3, c);   // layer 3: order the middle two

clang compiles the four-element network for int to 20 instructions — two loads, five rounds of one compare and two conditional selects (cmp, csel, csel), two stores — and no branch. The three- and five-element versions use the same __cond_swap plus a fused helper for three elements whose last two are already in order; they take 3 and 9 comparisons, the fewest any network for those sizes can use (4 elements take 5).

These networks only fire on partitions of exactly 3, 4 or 5 elements. The control above keeps them on in both builds, so the 2.88× it measures is the partition's alone; the networks fall inside the 1–8% that separates libc++ with its partition switched off from libstdc++.

4

the pivot and the safety net

Small Refinements

Above 128 elements libc++ picks its pivot as a median of medians of three: the median of three triples sampled from both ends and the middle. Nine samples land closer to the true median than three, which keeps the two sides of each partition more even. The heapsort fallback is unchanged, and never fires on random data. Both are inside the 1–8% that separates libc++ with its partition switched off from libstdc++.
