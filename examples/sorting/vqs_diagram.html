Vectorized Quicksort

Quicksort spends nearly all its time in one loop: partitioning. Replacing that loop's scattered in-place swaps with two sequential streams is what makes a SIMD version worth building.

Bramas, arXiv:1704.08579 · measured on Apple M5 (NEON), Highway, clang -O2

Classic quicksort partitions with Hoare's two-pointer scan: walk in from both ends, and whenever a pair is out of place, swap it. The comparisons are cheap, but the writes land wherever the pointers happen to be — scattered across the whole subarray.

The version here is libc++'s std::sort with one part replaced. It keeps std::sort's base case, its pivot rule, its depth limit and its recursion, and changes only the partition, using a SIMD instruction called CompressStore that packs the selected lanes of a register into contiguous memory. That single substitution turns the write pattern from random to sequential, and it is the only thing separating the two sorts in the measurements below.

Everything below is measured on Apple M5. The partition is portable Highway; at the NEON target the vector is 4 lanes of int32.

01The primitive: CompressStore

Load a block of lanes, compare all of them against a broadcast pivot in one instruction, then write each group out packed together. CompressStore skips the lanes the mask rejects and closes the gaps — the survivors land contiguously.

02One partition pass

The whole subarray streams through that block loop. Two counters, lc and rc, track how far each scratch buffer has filled. A short scalar loop mops up the elements that do not fill a whole vector, then both buffers are copied back over the original range.

03The inner loop in Highway

This is simd_partition from vqs_highway.cpp, the code behind the pass above. It is written once, against a vector of whatever width the target has.

const HWY_FULL(int32_t) d;                     // (1) the widest int32 vector on this target
const int N = (int)hn::Lanes(d);               //     4 on NEON, 8 on AVX2, 16 on AVX-512
const auto pivot_v = hn::Set(d, pivot);        // (2) pivot copied into every lane
int lc = 0, rc = 0;                            //     fill level of each scratch buffer

const int vend = lo + ((hi - lo) / N) * N;     // (3) last whole vector
for (int i = lo; i < vend; i += N) {
    const auto v       = hn::LoadU(d, a + i);  // (4) N elements, any alignment
    const auto lt_mask = hn::Lt(v, pivot_v);    // (5) one bit per lane: v < pivot
    const auto ge_mask = hn::Ge(v, pivot_v);    //     and its complement: v >= pivot
    lc += (int)hn::CompressStore(v, lt_mask, d, left_buf  + lc);   // (6) pack, append,
    rc += (int)hn::CompressStore(v, ge_mask, d, right_buf + rc);   //     advance by the count
}
for (int i = vend; i < hi; i++) {               // (7) fewer than N left: one at a time
    if (a[i] < pivot) left_buf[lc++] = a[i];
    else              right_buf[rc++] = a[i];
}
memcpy(a + lo,      left_buf,  lc * sizeof(int));   // (8) copy back: [ < pivot | >= pivot ]
memcpy(a + lo + lc, right_buf, rc * sizeof(int));
return lc;
  1. One source, every width. HWY_FULL names the widest vector the build targets, and Lanes says how wide that is, so the loop strides 4, 8 or 16 elements without a line changing.
  2. Broadcast the pivot once, outside the loop, so every comparison is lane against lane.
  3. Stop at the last whole vector. The vector loop never reads past the subarray.
  4. Load a block. LoadU accepts any alignment, so i can start anywhere.
  5. Classify every lane at once. Lt and Ge return masks — a true/false per lane — not branches. The two masks are complements, so every element goes to exactly one buffer.
  6. Pack and advance. CompressStore writes the selected lanes contiguously at the buffer's current end and returns how many it wrote; adding that count to lc or rc is the only thing the data decides. The loop has no branch on the values, just two pointers that move by a data-dependent amount. On AVX-512 this is one instruction (vpcompressd). AVX2 and NEON have none, so Highway looks up a permutation for the mask, shuffles the selected lanes to the front, and stores the whole vector; the lanes past the count are scratch that the next store overwrites.
  7. Finish the tail in scalar code — at most N−1 elements, and the only data-dependent branch in the function.
  8. Copy back, left buffer then right, so the range ends up as everything below the pivot followed by everything at or above it. Both buffers were filled front to back, so both copies are sequential.

04What it changes: the write pattern

Both partitions read every element once. The difference is entirely in where they write. Hoare writes in place, at two pointers that wander toward each other; CompressStore writes forward into two buffers and never revisits an address.

05Where the recursion stops

Partitioning is only worth it while the subarray is large. Below 24 elements vqs hands the range to std::sort, which at that size never partitions and runs libc++'s insertion sort — exactly what std::sort does with its own small partitions. The leaves cost the same in both sorts.

CompressStore is behind at n = 32, even from 64 to 256, and ahead from n = 512 by a steady 1.10–1.17× all the way to n = 1 048 576. The lead does not grow with n, and every size here fits in the M5's 16 MB L2, so it is not a cache effect. It is also a contest between two branch-free partitions: on int data, libc++'s std::sort partitions with a bitset scheme whose comparisons never mispredict.

Why the win is modest

vqs beats std::sort by only 1.10–1.17× on the M5 because it is not racing a scalar partition. libc++'s bitset partition is already branch-free, and the compiler has already vectorized its comparisons with the same 4-lane NEON instructions vqs uses. Both partitions run the same comparisons on the same hardware, and differ only in how they move the elements afterwards.

The big win is already in std::sort. A branchy partition mispredicts about half its comparisons on random data, and switching libc++'s bitset partition off makes std::sort 2.9× slower at a million elements. vqs removes the same mispredictions, so the 2.9× is not on the table for it; the bitset partition has already taken it.

Four lanes and no compress instruction. A NEON register holds 4 int32, so each pass of vqs's loop classifies only 4 elements. NEON also has no compress instruction, so Highway builds each CompressStore from several: it turns the mask into a table index, loads a permutation, shuffles with tbl, stores the whole vector and counts the mask bits. That is about 13 instructions to pack 4 elements, done twice per block, one for each side. libc++'s classification loop, compiled from the same source in our build, handles 16 elements in about 48 instructions, roughly 3 per element; it then pays only for the elements that are on the wrong side.

What is left is moving the elements. vqs writes every element into a scratch buffer and copies it back; libc++ swaps only the misplaced ones, in place, within two 64-element blocks. On the M5 that difference is worth 10–17%. CompressStore was designed for AVX-512, where one register holds 16 lanes and one vpcompressd packs all of them; that is the setting where it has more to gain, but it was not measured here.

How it was measured

Every sort gets a different random input, drawn from a pool of distinct arrays that both sorts share at each n. A comparison sort's branches depend on the data; sort the same array over and over and the branch predictor learns it, and the branchy sort runs several times faster than it ever will on new data. The program also pins itself to a performance core and warms the clock before timing, and prints the clock it measured.
