Three Techniques
of std::sort

std::sort is not one algorithm. It combines three sorting techniques — insertion sort, quicksort's partition and heapsort — with two checks that decide which one handles each piece of the array. This page measures GCC's libstdc++. clang's libc++ has additional optimizations. (libc++).

New to these three algorithms? Sort Mechanisms traces how each one moves data, step by step: insertion sort, quicksort's partition, and heapsort.

Isolating each decision's contribution needs a control. This repository's quicksort.cpp uses a median-of-three Hoare partition of the same kind libstdc++ uses internally (__unguarded_partition), with no cutoff and no depth limit, recursing all the way to partitions of one. Both are compiled by the same compiler, GCC 16, so the gap between them is the value of decisions 1 and 2.

How much can the cutoff be worth? Instrumenting quicksort.cpp to record wall time by node size, for one sort of 1,048,576 random ints, answers that directly (quicksort_breakdown.cpp).

“Node size” is the size of one partition call, counting calls on two or more elements; “excl. time” is that call's own partition-loop cost with every descendant call's time subtracted out. The technique is an outermost-entry guard — time a call on a partition of ≤ T elements as a whole, and nothing inside it again — applied at nine thresholds, with bands from successive differences and the 10 ns cost of each pair of clock reads measured and subtracted. Rows don't overlap and sum to the 46.7 ms total. Every figure is the best of 7 sorts of different random arrays, and the median of 5 runs.

Only 15.6% of quicksort's time is spent in the ≤16 partitions. The other 84.4% — nodes from 17 elements up to the root — is the median-of-three Hoare partition that std::sort also runs, on the same pieces, the same number of times. That makes a sharp prediction: std::sort should cost what quicksort costs with its ≤16 leaves removed, plus whatever its one final insertion pass costs. The chart below draws that middle line.

1

technique 1 · insertion sort

The Leaf

Where the cutoff fires before quicksort ever partitions.

Insertion sort shifts each new element backward past every larger element already placed — quadratic in the worst case, but with no recursion, no pivot selection, and a strictly sequential access pattern. At n = 16 that quadratic cost is at most 120 simple compare-and-shift steps; the constant factor is what matters, and insertion sort's is tiny.

Plain quicksort's constant factor is not. At n = 16 it still recurses roughly four levels deep, and every level pays a function-call frame, a median-of-three selection, and a Hoare partition loop before it has sorted anything. std::sort's first decision is to skip all of that: at 16 elements or fewer it never partitions, and the final insertion-sort pass is the whole sort. Here the cutoff is the entire difference, and it is worth 2×.

2

technique 2 · quicksort partition

The Middle

Where both implementations run the same partition — and cost the same, apart from the leaves.

Above the leaf, both algorithms do the same thing: pick a median-of-three pivot, partition with two inward-walking pointers, recurse on each side. The only difference is the bottom of the tree. Quicksort recurses into every partition of 16 or fewer elements; std::sort leaves them alone and finishes them all in one linear pass at the end.

3

technique 3 · heapsort

The Safety Net

Where a decision built for hostile input stays dormant on ordinary data.

Heapsort is std::sort's second decision: if recursion ever passes depth 2·log₂n, abandon quicksort and switch to heapsort, which is slower on average but has no input that makes it quadratic. On random data it never runs.

Nor does it run on the inputs people usually worry about. Already-sorted, reverse-sorted and all-equal arrays are easy for a median-of-three pivot: the median of the first, middle and last elements of a sorted range is its true median, so every split is even. (Sorted input is the worst case for a quicksort that pivots on the first element, which is the problem median-of-three solves.) The fallback is for inputs built to defeat median-of-three itself:

  • Organ pipe — ascending to the middle, then descending. Worked through below.
  • Median-of-three killers — sequences arranged so that every pivot is the second-smallest element of its range. Musser designed introsort, with this fallback, after showing that such inputs drive median-of-three quicksort to O(n²).
  • An adversary — McIlroy's “killer adversary” assigns values during the sort itself, choosing each answer so the pivot turns out as bad as possible. It defeats any quicksort whose pivot choice it can watch, and matters wherever an attacker controls the data being sorted.

Example: an organ pipe

The ends of an organ pipe are both small and its middle is the largest value, so median-of-three always lands on something near the bottom.

At full size the same thing repeats at every level. With 65,536 elements the first split leaves 3 on the small side; the small side doubles each level after that, so the large side shrinks by only a few percent at a time:

The recursion reaches the depth limit, 2·log₂65,536 = 32, where random input never goes past 25, and libstdc++ hands the remaining ranges to heapsort — 125 times in all. Counting calls to libstdc++'s heapsort with a debugger confirms it: 125 for this organ pipe, one for McIlroy's adversary, and zero for random, sorted, reverse-sorted and all-equal input. It is insurance, and on the data this page measures it never pays out.

Three techniques, and — because this repository's plain quicksort runs the same kind of partition libstdc++ uses internally — a fair way to measure what they're worth. In the middle and above, std::sort and quicksort do the same partitioning at the same cost; the whole difference is at the bottom of the tree, where one final insertion pass does the leaves' work for about half of what recursing into them costs. That is worth 2× at n = 16 and settles to 1.1–1.2× from n = 128 up. The depth-limited heapsort fallback never runs on this data; its payoff only shows up on hostile inputs like the organ pipe above.

clang's libc++ is 3× faster than this at a million elements, with the same three techniques. What libc++ Adds shows where that comes from.
