Reorder Buffer Snapshot

One moment inside an out-of-order core while it runs the scan loop from quicksort.cpp, while (a[++i] < pivot) {}. The branch predictor has guessed "keep scanning" twice, so the core is already two iterations ahead of what it has proven.

The loop

L1: add  x9, x9, #1           // ++i
    ldr  w8, [x0, x9, lsl #2]  // a[i]
    cmp  w8, w10               // a[i] vs pivot
    b.lt L1                    // keep scanning while a[i] < pivot

Rename gives every result its own physical register. In the diagram, x9 becomes p11, p14, p17 in successive iterations, w8 becomes p12, p15, and the flags become f13, f16. That's why iteration 2 can run while iteration 1 is still waiting: the only true dependencies left are read-after-write (RAW).

The five states

decoded

Fetched and decoded, but not yet renamed or given a ROB entry. Before the pipeline.

waiting

In the ROB and the scheduler. At least one source register hasn't been produced yet.

executing

Operands ready, issued to a functional unit. In the pipeline.

completed

Result written to its physical register. Still waits for everything older to finish.

retired

Reached the head while completed. Its result becomes architectural state and the entry is freed.

When the branch resolves

The load returns, then cmp f13 runs, then b.lt f13 executes and checks its prediction. The same speculative work then goes one of two ways.

Does branch prediction wait for the instruction to be decoded?

A question from class.

No. The predictor sits at the very front of the pipeline, ahead of decode, and works from addresses rather than instructions. The iteration 3 instructions in the front end above show this: they were fetched because the predictor called b.lt f16 taken long before that branch could execute.

  • What it sees: the address of the block about to be fetched, plus the history of recent branch outcomes.
  • Branch target buffer (BTB): a cache indexed by address. It says whether the block holds a branch, where it is, what kind it is, and its target, so the front end knows a branch is there before any bytes are decoded.
  • Direction predictor: a TAGE-style table indexed by the address hashed with history says taken or not taken. A return stack predicts the target of each ret.
  • Decoupled front end: the predictor runs ahead, filling a queue of fetch addresses that fetch and decode follow. If it had to wait for decode, every taken branch would leave a gap of several cycles.

Decode still has two jobs. The first time a branch is seen, the BTB has no entry, so fetch falls through. When the decoder finds a direct jump or call, it redirects fetch itself, because the target is encoded in the instruction. That costs a few cycles, far less than a misprediction. A conditional branch the BTB missed is usually treated as not taken until it executes. Decode also corrects stale BTB entries that claim a branch where there isn't one.

Whether a prediction was right is only known when the branch executes, as the second figure shows. The partition loop's branches are long past the BTB-miss stage: the predictor knows exactly where they are and where they go. What it can't know is their direction, because a[++i] < pivot on random data is close to a coin flip.
