## 1 · What a vector is

A normal register holds one number. Add two of them and you get one sum.

A **vector register** is wider — 128, 256, or 512 bits — and the hardware
agrees to treat those bits as *several numbers side by side*. A 128-bit
register can be read as four 32-bit integers, or two 64-bit doubles, or
sixteen bytes. Each slot is called a **lane**.

The point is what happens when you operate on one. A vector instruction
applies the same operation to every lane **at the same time**:

```
             one 128-bit register, read as 4 lanes of 32 bits

                lane 3      lane 2      lane 1      lane 0
            +-----------+-----------+-----------+-----------+
         a  |     7     |     3     |     9     |     4     |
            +-----------+-----------+-----------+-----------+
                  |           |           |           |
                  ==          ==          ==          ==   <-- ONE instruction
                  |           |           |           |
            +-----------+-----------+-----------+-----------+
         b  |     7     |     5     |     9     |     1     |
            +-----------+-----------+-----------+-----------+
                  |           |           |           |
                  v           v           v           v
            +-----------+-----------+-----------+-----------+
       dst  |   all 1s  |     0     |   all 1s  |     0     |
            +-----------+-----------+-----------+-----------+
                equal     not equal     equal     not equal
```

Four comparisons, one instruction, one core, one thread. That is **SIMD** —
*Single Instruction, Multiple Data*.

### SIMD is not concurrency

This is the distinction worth fixing early, because the vocabulary overlaps
with the parallelism we do later in the course.

| | SIMD | Threads |
|---|---|---|
| How many instruction streams | one | several |
| How many cores | one | several |
| What you have to reason about | lane layout | races, locks, ordering |
| What limits the speedup | lanes per register | cores, and Amdahl's law |

Lanes never talk to each other. Lane 2 cannot read lane 1's value as part of
the same operation, and there is no ordering question between them because
they all finish together. That is exactly why vector code has no locks and no
data races — and also why some algorithms resist vectorization completely.

Like the ILP of Lecture 03, this is **parallelism without concurrency**: the
core is doing more per instruction, not running more instruction streams.

### Lanes are the speedup

The ceiling on a vector speedup is the number of lanes, and nothing else:

```
lanes = register width in bits / element width in bits
```

A 256-bit register holds 8 `int32` lanes, so 8x is the ceiling for `int32`
work. Use `double` instead and the same register holds 4, so the ceiling
halves. **The data type you choose changes your speedup**, which is not true
of any optimization in Lecture 06.

You will not reach the ceiling. Loads, stores, the loop tail, and anything
that has to move data between vector and scalar registers all cost. But the
lane count tells you immediately whether a transformation is worth attempting.

## 2 · A computing example

Count how many elements of an array equal some target.

The scalar version is the obvious loop — look at one element, compare, maybe
add one:

```c
long count_ints(int* data, long n, int target) {
    long count = 0;
    for (long i = 0; i < n; i++) {
        if (data[i] == target) {
            count += 1;
        }
    }
    return count;
}
```

One element per iteration, and a branch per element.

The vector version changes the shape of the loop. Load eight elements at once,
compare all eight against the target in one instruction, and add up how many
matched:

```c
long count_ints(int* data, long n, int target) {
    long count = 0;
    long clean_end = (n / 8) * 8;     // largest multiple of 8 <= n
    long i = 0;

    for (; i < clean_end; i += 8) {
        // compare data[i] .. data[i+7] against target, all at once
        int number_equal = /* one vector compare, then count the matches */;
        count += number_equal;
    }

    for (; i < n; i++) {              // the tail: 0-7 leftover elements
        if (data[i] == target) count += 1;
    }
    return count;
}
```

Two things are worth noticing, because they show up in *every* hand-written
vector loop:

**The main loop steps by the lane count, not by one.** Eight elements per
iteration means `i += 8`.

**There is a tail.** `n` is rarely a multiple of 8, so the leftover elements
are handled by an ordinary scalar loop afterwards. This is the same tail
problem from Lecture 06's unrolling discussion, and it is unavoidable: a
vector instruction processes a whole register or nothing.

Notice also what disappeared: **the branch**. The scalar loop has an
unpredictable `if` per element — the thing Lecture 04 spent its time on. The
vector version has no per-element branch at all. The comparison produces a
value rather than a decision. That is often a bigger win than the lane count
suggests, and it is why vectorizing frequently beats its own theoretical
ceiling-based estimate on branchy data.

## 3 · Three ways to program a vector unit

The same loop can be written at three levels. They are not competing styles —
you will use all three on the same problem, usually in this order.

### Let the compiler do it

Write the plain scalar loop, turn on `-O2` or `-O3`, and let the
auto-vectorizer rewrite it. This is the right first move nearly always: it is
free, it is portable, and modern vectorizers are good.

The catch is that it happens silently and it fails silently. Always ask:

```bash
g++     -O3 -fopt-info-vec           -c count.cpp   # what it vectorized
clang++ -O3 -Rpass-analysis=loop-vectorize -c count.cpp   # and why it did not
```

A vectorizer needs to know the trip count before the loop starts, so it can
plan "`n/8` whole vectors, then the remainder." Anything that makes the trip
count unknowable — an early `return`, a data-dependent exit, a pointer it
cannot prove doesn't alias — and it gives up and emits scalar code.

### Write intrinsics

An **intrinsic** is a C function that compiles to exactly one machine
instruction. You get the instruction you want without writing assembly, and
the compiler still handles register allocation for you.

```c
__m256i eq = _mm256_cmpeq_epi32(v, wanted);   // compare 8 int32 lanes
```

The naming is mechanical once you see it: `_mm256` is the register width,
`cmpeq` is the operation, `epi32` means "packed 32-bit integers." Intel's
[intrinsics guide](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html)
is the reference, and it gives the pseudocode for each one, lane by lane.

The cost is portability: `<immintrin.h>` does not exist on Apple silicon, so an
AVX2 routine simply has no equivalent on the M5. This is a real problem, not a
theoretical one, and it is why the example directory ends up using a portable
library instead.

### Read the assembly

You do not usually *write* vector assembly, but you should be able to read it,
because it is how you confirm what actually happened:

```assembly
vpcmpeqd  ymm1, ymm0, ymmword ptr [rdi + 4*rcx]   ; compare 8 lanes
vpmovmskb r9d, ymm1                               ; lane results -> bitmask
popcnt    r9d, r9d                                ; count the set bits
add       rax, r9
```

`ymm` registers are 256-bit; `xmm` are 128-bit; `zmm` are 512-bit. If you see
`ymm` in the output, it vectorized. If you see only `eax`/`rcx`, it did not,
whatever the optimization report claimed.

[Compiler Explorer](https://godbolt.org/) is the fastest way to look — paste
the loop, pick a compiler and flags, read the right-hand pane.

### A fourth way: a portable SIMD library

Intrinsics lock a routine to one instruction set. A portable SIMD library
writes the same algorithm against an *abstract* vector type and compiles it to
whatever the target has — NEON, AVX2, AVX-512, SVE, RISC-V V.

This course uses [Google Highway](https://github.com/google/highway), and the
[example directory](../examples/vectorization/README.vectorization.md) shows
the same source compiling to AVX2 on the Ryzen and NEON on the M5. The key
idea there is that the lane count becomes a runtime value rather than a
constant you hard-code — which is the only way to write for hardware whose
vector width is not known until the program runs.

### Side by side: what the compiler emits, and what you emit

It is worth doing this comparison once, on the counting loop above, because the
result is not the one most people expect.

Compile the plain scalar loop at `-O3 -mavx2` and ask what happened:

```bash
$ g++ -O3 -mavx2 -fopt-info-vec -c count.cpp
count.cpp:3:24: optimized: loop vectorized using 32 byte vectors
count.cpp:3:24: optimized: loop vectorized using 16 byte vectors
```

Two lines for one loop: the main body at 32 bytes (256-bit `ymm`) and the tail
at 16 (128-bit `xmm`), because the leftover elements are worth vectorizing too
but not at full width. It vectorized.

So we now have two vector implementations of the same function
— one the compiler wrote, one we wrote — and we can read both. Here is the
compiler's inner loop, and ours, side by side:

```assembly
; ---- COMPILER, from the plain scalar loop ----      8 elements, 9 instructions
vpcmpeqd     (%rax), %ymm3, %ymm0     ; compare 8 lanes at once
addq         $32, %rax
vpmovsxdq    %xmm0, %ymm2             ; widen the low 4 results to 64-bit
vextracti128 $0x1, %ymm0, %xmm0       ; pull out the high 4 results
vpsubq       %ymm2, %ymm1, %ymm1      ; accumulate, 64-bit lanes
vpmovsxdq    %xmm0, %ymm0             ; widen the high 4 to 64-bit
vpsubq       %ymm0, %ymm1, %ymm1      ; accumulate, 64-bit lanes
cmpq         %rdx, %rax
jne          .L4

; ---- OURS, hand-written intrinsics ----            8 elements, 5 instructions
vpcmpeqd     (%rcx,%rax,4), %ymm3, %ymm1
addq         $8, %rax
vpsubd       %ymm1, %ymm0, %ymm0      ; accumulate, 32-bit lanes
cmpq         %rax, %rdx
jg           .L3
```

Both compare eight lanes per instruction — the compiler is not using a
narrower vector than we are. The difference is entirely in what happens
*after* the compare. The compiler splits its eight results in half, widens
each half from 32-bit to 64-bit, and accumulates into 64-bit lanes. That is
four extra instructions for the same eight elements.

**Why?** Look at the C, not the assembly:

```c
long count = 0;          //  <-- 64 bits
```

The count is a `long`. The compiler has to return exactly what the scalar loop
would return, for *every* `n` — including an `n` large enough that a 32-bit
counter would overflow. So it must accumulate in 64-bit lanes, and a 256-bit
register holds only four of those. Our version accumulates in 32-bit lanes,
which is faster and is **only correct because we assumed something the
compiler is not allowed to assume**: that the answer fits in 32 bits.

That is a testable claim, so test it. Change one word in the scalar loop —
`long count` to `int count` — and recompile, touching nothing else:

```assembly
; ---- COMPILER, from the scalar loop with `int count` ----
vpcmpeqd     (%rax), %ymm2, %ymm0
addq         $32, %rax
vpsubd       %ymm0, %ymm1, %ymm1      ; accumulate, 32-bit lanes
cmpq         %rdx, %rax
jne          .L4
```

Instruction for instruction, that is our hand-written loop. The widening is
gone. The compiler found the same trick — subtract the all-ones compare result
instead of masking and adding — the moment the semantics allowed it.

The timings agree. 16384 `int32` values, L1-resident, pinned and warmed,
`g++ -O3 -mavx2`:

| version | ns/element | speedup |
|---|---:|---:|
| compiler, `long count` | 0.0988 | 1.00x |
| compiler, `int count` | 0.0493 | **2.01x** |
| hand-written intrinsics | 0.0493 | **2.01x** |

**The intrinsics bought nothing.** Every bit of the 2x came from relaxing the
accumulator width, and the compiler did it by itself once it was permitted to.
The version that took an afternoon to write and only runs on x86 ties the
version that took one word.

This generalizes, and it is the reason auto-vectorization is the first thing
to try:

> When the compiler produces worse vector code than you would, the cause is
> usually a **guarantee it cannot drop**, not an optimization it cannot find.

You have met this shape twice already. In Lecture 06, the compiler would not
vectorize a floating-point reduction because addition is not associative — it
needs `-ffast-math` to be allowed to reorder. In Lecture 04, it would not hoist
a loop-invariant test because it could not prove the pointers did not alias.
Same pattern: not a missing derivation, a missing permission.

So before reaching for intrinsics, find out which guarantee is costing you.
It is often a type, a `restrict`, or a flag — and unlike intrinsics, the fix
stays portable. On the M5 this same source compiles to NEON unchanged; the
intrinsics version does not compile there at all.

Intrinsics are still the right answer when the compiler cannot vectorize at
*all* — which is exactly the case the example directory is built around.

## 4 · What the hardware gives you

### x86: three generations, still all present

Each generation doubled the register width, and every one of them is still in
use — a current chip supports all three, and the compiler picks based on your
`-march` / `-m` flags.

| | Register | Width | `int32` lanes | `float` lanes | `double` lanes |
|---|---|---|---|---|---|
| **SSE / SSE2** | `xmm` | 128-bit | 4 | 4 | 2 |
| **AVX / AVX2** | `ymm` | 256-bit | 8 | 8 | 4 |
| **AVX-512** | `zmm` | 512-bit | 16 | 16 | 8 |

SSE2 is guaranteed on every x86-64 chip — it is part of the base architecture,
which is why the compiler will use it without being asked. AVX2 and AVX-512
must be requested (`-mavx2`, `-mavx512f`) or inferred (`-march=native`), and a
binary built with them will crash on a machine that lacks them.

AVX-512 also added **masks** — a separate register holding one bit per lane,
so an instruction can operate on some lanes and leave others alone. That makes
`if` statements inside vector loops far more tractable than they are in AVX2.

### Apple silicon: NEON at 128 bits

The M-series has **NEON**, 128-bit registers, and that is the whole story for
width:

| | Register | Width | `int32` lanes | `float` lanes | `double` lanes |
|---|---|---|---|---|---|
| **NEON** | `v0`–`v31` | 128-bit | 4 | 4 | 2 |

Narrower than AVX2, but there are 32 of them, and the cores can issue several
NEON operations per cycle. ARM's **SVE** allows wider and *variable* widths,
where the vector length is not known at compile time — that is the model
Highway's scalable types are written for — but the M-series implements NEON.

### The honest caveat

A 512-bit register is four times the width of a 128-bit one. It is **not**
four times the speed.

Wider registers only pay if the execution units behind them are equally wide,
and that varies by chip even within one ISA — several AVX-512 implementations
execute 512-bit operations by splitting them internally, so you get the wider
registers and the mask registers without the throughput. Some chips also drop
their clock when heavy 512-bit code runs, which can make wide code slower
overall.

Which is the same lesson as Lecture 06, in new clothes: **the specification
tells you the ceiling, and the measurement tells you the speedup.** The
example directory measures 2–3.5x from 256-bit AVX2 and about 1.5–1.8x from
128-bit NEON on the same source — both well under their lane counts, and both
worth having.
