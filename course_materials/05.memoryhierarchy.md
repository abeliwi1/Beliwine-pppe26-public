## Memory is an abstraction

Your program is handed a promise the hardware does not keep:

  * a single flat address space of byte-addressable locations
  * every location costs the same to reach
  * a byte is the unit you ask for

None of the three is true. What is actually there is a **steep hierarchy** of
caches whose levels differ in three ways at once — **latency**, **capacity**,
and **who can see them**. Nothing in your source code says which level a given
load will hit. Your access pattern decides it, and the difference between the
best and worst answer is larger than most algorithmic improvements you will
ever make.

## Where this picks up from Lecture 04

Lectures 03 and 04 were about the core: it executes in the order the data
allows, it speculates past branches, and it hides a great deal of work behind
out-of-order execution. All of that machinery has one job, and it is worth
naming plainly: **keeping the core busy while it waits for memory.**

This lecture is about what it is waiting for. Lecture 06 is what you do about
it — every transformation there relieves a bottleneck defined here.


## What to carry into Lecture 06

Four numbers and one question.

| | |
|---|---|
| **48 KB** | the L1 working set you are tiling toward |
| **64 bytes** | the unit everything moves in; what you pad to |
| **130×** | what a DRAM miss costs against an L1 hit |
| **12-way, 64 sets** | why a power-of-two row length is a trap |

And the question to ask of any loop before you change it: **of every 64 bytes
this forces the machine to move, how many does it use?** Lecture 06's five
transformations are five different answers to it — interchange fixes the
stride, tiling fixes the working set, fusion fixes the number of passes. None
of them makes sense until the bottleneck is named.
