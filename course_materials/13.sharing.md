# The Performance of Sharing

Learning goals:
  * Know that cores share data one cache line at a time
    * coherence: a write needs the only copy, so the line moves
    * the cost of the move depends on where the two threads run
  * Tell true sharing from false sharing
    * true sharing: threads communicate through a variable, so the line must move
    * false sharing: threads use different variables on one line, so the line
      moves when it doesn't need to
  * Predict when sharing is expensive
    * an update that must complete (atomic, fence, lock) pays for the whole trip
    * an ordinary write goes to the store buffer, so many writes share one trip
  * Fix false sharing: pad to the line size, or keep updates in a local
    variable

## Cache Coherence

  * each core has a private L1 (and on the Ryzen, a private L2)
  * the unit of coherence is the line: 64 bytes on the Ryzen, 128 on the M5
  * MESI is the protocol that keeps the private caches agreeing on each line:
    it marks every cached copy Modified, Exclusive, Shared or Invalid. Many
    cores may hold a line to read it, but a core that writes must hold the
    only copy, so every other copy is invalidated.
  * figure: [sharing_topology.svg](images/sharing_topology.svg) — which caches
    each pair of cores has in common

## Sharing: the cost of a handoff

  * details and results: [README.sharing.md](../examples/sharing/README.sharing.md)
  * `pause` mode: two threads take turns writing one atomic variable
  * nothing overlaps, so each handoff pays the full trip of the line
  * the trip depends on how far the line travels (Ryzen, `pause`):
    * 12 ns between the two hardware threads of one core (a shared L1)
    * 19 ns between two Zen 5 cores, 29 ns between two Zen 5c cores (a
      shared L3)
    * ~170 ns between a Zen 5 and a Zen 5c core: separate L3s, so the line
      crosses the interconnect
  * the M5 shows the same pattern: 52 ns between two performance cores,
    ~150 ns between a performance and an efficiency core
  * measure at full clock: a core that only waits doesn't boost, so in
    `sharing.cpp` each thread runs a busy loop for a second before timing
    (on one core, 25.7 ns from idle against 11.9 ns at full clock)
  * `spin` mode: waiting impatiently pulls the line back and slows the
    writer; why spin loops use a pause hint
    * figure: [spin_vs_pause.svg](images/spin_vs_pause.svg), in
      [README.sharing.md](../examples/sharing/README.sharing.md)
    * on the Ryzen, `spin` handoffs take 2.5–2.7× as long as `pause` within a
      core or a cluster; across the clusters the trip dominates, and the two
      are about the same
    * on the M5's performance cores the two are the same (52 ns); why is an
      open question

## False sharing: paying for data you don't share

  * details: the `false` modes in [README.sharing.md](../examples/sharing/README.sharing.md)
  * per-thread counters packed into one line: see the
    [False Sharing](https://claude.ai/artifact/2Y16D2StfxCmXQKdZ24x7Q) explainer
  * figure: [sharing_methods.svg](images/sharing_methods.svg)
  * the surprise: plain `false` costs ~1 ns against 0.2–0.3 ns padded, not
    20–170 ns
    * the store buffer absorbs ordinary writes; one transfer commits many
  * add a fence or make the increment atomic and the cost returns
    (`false-fence`, `false-atomic`), and it grows with distance
    * a fenced increment: about the same as padded on one core (18.5 against
      17.9 ns), 40 ns more across the clusters
    * an atomic increment: 2.5–3× the padded cost
  * locks, atomic counters and reference counts are updates of this kind

## Fixes

  * pad or align to the line size: `alignas(64)`, or
    `std::hardware_destructive_interference_size`
    * the line size isn't portable: 64-byte padding fails on the M5
  * accumulate in a local variable and write the shared one once
    (OpenMP `reduction`, Cilk reducers do this for you)
  * place threads that communicate close together

## What to carry forward

  * sharing costs a line transfer, and the price is set by the topology
  * ordinary writes hide it; atomics, fences and locks expose it
  * false sharing is a layout bug: find it by measurement, fix it with padding
    or local accumulation
  * next: synchronization, where we share on purpose
