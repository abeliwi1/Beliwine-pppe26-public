# Loop Optimizations

Learning goals:
  * Understand why loops get disproportionate attention
    * the leverage argument: fix one iteration, benefit a billion times
    * loop independence as the legality test every transformation shares
  * Know the five classical transformations and what each one is actually for
    * unrolling, fusion, fission, interchange, tiling
    * each relieves a *specific* bottleneck
  * Understand why the textbook version of each rule fails on real hardware
    * loop-control overhead is already free on an out-of-order core
    * `B <= associativity` and `2B²·8 <= L1` both mispredict the tile
    * the right fission width is a property of the ISA, not of the algorithm
  * Recognize when the data layout, not the loop, is the problem
    * cache set conflicts, and why padding beats blocking
  * Be able to take a measurement you can trust
    * heterogeneous cores, clock ramp, and why min-of-N does not save you
    * loop-invariant hoisting, and how a benchmark announces it is lying

## Where this picks up from Lectures 03, 04 and 05

Lecture 03 established that a modern core executes in the order the *data*
allows, not the order you wrote, and that its reorder buffer will find
parallelism you did not explicitly ask for. Lecture 04 was the programmer's
side of one specific hardware behaviour: what you do about a branch once you
know it is expensive.

[Lecture 05](05.memoryhierarchy.md) supplies the bottleneck this one spends
its time relieving. Three results from it are assumed throughout and worth
having in front of you:

  * **memory moves in 64-byte lines**, so the useful question about a loop is
    what fraction of each line it uses — that is interchange, in §3 below
  * **a DRAM miss costs 130 L1 hits**, roughly 500 instructions of waiting —
    that is the whole case for tiling, in §5
  * **L1 is 12-way with 64 sets**, so a power-of-two row length puts a whole
    column into one set — which is why §5 ends with padding beating blocking

This lecture is the same move, applied to the loop. We have a machine that
aggressively hides work, and we have five classical transformations that
predate that machine by decades. The interesting question is not "what are the
five transformations" — it is **which of them still do anything, and why.**

The answer is less comfortable than the textbook suggests. One of the five
does nothing at all on this hardware. One of them is beaten by a one-word
change to a declaration. And in three of the five, the rule you would use to
pick the parameter gives the wrong parameter.

## Why loops at all

A program runs thousands of distinct lines over its lifetime, but a handful of
loop bodies account for nearly all the actual work, because each one executes
not once but millions or billions of times. Shave one cache miss off a single
iteration of a loop that runs a million times and you have removed a million
cache misses. **Fix it once, benefit every iteration.** That leverage is why
loops get attention out of all proportion to their share of the source.

It is also why loops admit a *fixed toolkit*. A loop body is the same
operation applied to different data, iteration after iteration, so a handful
of general rewrites — reorder the iterations, split the loop, merge two loops,
do several at once — transfer across completely unrelated problems.

### The legality test they all share

Every one of these rewrites reorders, splits, merges, or overlaps iterations.
That is only valid if the iterations are **independent** — no value written in
one iteration is read by another. A loop with a genuine loop-carried
dependency (a running sum, a recurrence) is not a candidate for any of them.

[The directory README](../examples/loop_optimizations/README.loops.md) works through
what each transformation specifically needs independence *for*, and makes an
important secondary point: independent is not the same as safe to reorder
bit-for-bit. Floating-point addition is not associative, so even a legal
reordering of a reduction can change the last bit — which is why the compiler
will not vectorize an FP reduction without `-ffast-math`.

> [loop_carried_dependency.html](../examples/loop_optimizations/loop_carried_dependency.html)
> — two loops over the same eight numbers on one shared clock. The dependent loop
> passes a baton (the running total `s`) from box to box and needs eight ticks; the

## The five, and the bottleneck each one relieves

This is the table to carry out of the lecture. The transformation is never the
point; the bottleneck is.

| Transformation | Relieves | Measured here |
|---|---|---|
| [Unrolling](../examples/loop_optimizations/loop_unrolling.md) | loop-control instruction issue | **1.0x** — nothing |
| [Fusion](../examples/loop_optimizations/loop_fusion.md) | passes over memory | **2.02x** (ceiling is 2x) |
| [Interchange](../examples/loop_optimizations/loop_interchange.md) | cache line utilisation | **6.29x** |
| [Fission](../examples/loop_optimizations/loop_fission.md) | register pressure | **4.28x** |
| [Tiling](../examples/loop_optimizations/loop_tiling.md) | re-reads of data that already came in | **3.0x** on matmul; on transpose, padding beats it |

Note what that first row means. If you apply a transformation without knowing
which resource your loop is short of, unrolling's 1.0x is the result you
should expect. The bottleneck is the thing you diagnose; the transformation is
just the response.

## 1 · Unrolling — the one that does nothing

Start here, because it is the most instructive result in the directory.

The classical argument: each iteration pays for an increment, a compare, and a
branch. Do four elements per iteration and you pay that once instead of four
times. On a machine from 1990 this is obviously correct.

Measured at `-O1`, a 4x unrolled sum is **1.01–1.04x** — flat across every
working set from 8 KB to 64 MB. Duff's Device, the classic tail-handling
trick, is consistently ~5% *slower*.

The explanation is one number. The scalar loop runs at **1.0 cycles per
element**, at every level of the memory hierarchy, including 64 MB where every
line comes from DRAM. One element per cycle is exactly the latency of the
dependent chain through the accumulator: `s += data[i]` must wait for the
previous add, and an integer add has 1-cycle latency.

So the loop is sitting on its dependency floor, and the loop-control
instructions issue on other ports *in the same cycles*, costing nothing. The
branch predictor gets the back-edge right every time.

> **You cannot speed up a loop by deleting work that was already free.**

This is Lecture 03 cashing out. The reorder buffer is why loop overhead
disappeared, and the transformation designed to remove that overhead has
nothing left to remove.

### What unrolling is actually for

Change one thing — four independent accumulators instead of one:

```cpp
s0 += data[i];  s1 += data[i+1];  s2 += data[i+2];  s3 += data[i+3];
```

Same instruction count, same memory traffic. **1.65x**, because four
independent chains can be in flight at once instead of one. That is the
multiple-accumulator technique from Lecture 01 and [../examples/ILP/](../examples/ILP/)
— and you cannot write it without an unrolled body.

At `-O2` the same thing happens a second time, with the compiler as the
beneficiary: GCC vectorizes the unrolled kernels (**2.03x**) and declines to
vectorize the scalar loop. Checked with `-fopt-info-vec`. The unrolled body is
what gives the vectorizer four independent loads to pack.

> **Unrolling is an enabler, not an optimization.** Unroll when you want the
> wider body for something else. Unrolling for its own sake — and hand-written
> tail tricks like Duff's Device — are for machines that no longer exist.

## 2 · Fusion — the one that hits its ceiling exactly

Mean and variance. Variance needs the mean, and the mean needs a full pass, so
the naive version reads a 381 MB array twice. Rewriting with
Var(X) = E[X²] − E[X]² lets both accumulate in one pass: **2.02x**.

Two reads becoming one read caps this at 2x, and we got 2.02x — meaning the
extra multiply per element in the fused body is genuinely free, absorbed while
the core waits on DRAM. That is the regime fusion is for. It does not reduce
arithmetic; it reduces trips to memory.

### The counterexample in the same file

Welford's algorithm is the textbook numerically-stable single-pass method. It
reads the array once — identical memory traffic to the fused version — and
runs at **0.31x**, three times *slower* than just doing two passes.

It costs a floating-point divide per element (15–20 cycles against 4–5 for a
multiply), and each iteration's running mean depends on the previous
iteration's, so the divides serialize instead of pipelining. It converted a
memory-bound loop into a compute-bound one.

> **Fusion is only a win if the fused body stays cheap enough to remain
> memory-bound.**

There is also a free diagnostic here, which we will use again below: warming
the core's clock changes the cache-bound examples in this directory by ~1.4x
and changes these numbers by almost nothing. **A loop whose time does not
respond to core frequency is limited by the memory system, not the core.**

## 3 · Interchange — the free one

Matrix-vector multiply, `y = A·x`, 4096×4096. Swapping the loop order so the
inner loop walks the rightmost index: **67.2 ms → 10.7 ms, 6.29x**, with
identical results to the last bit (`max_err = 0`).

Two multiplicative effects. Stride-1 access uses all 8 doubles in every
64-byte line; the stride-32KB column access uses 1 of 8 and discards the rest
— 8x the memory traffic for the same arithmetic, which is exactly the stride
sweep from [Lecture 05](05.memoryhierarchy.md#4--memory-access-patterns). And the stride-1 stream is
trivially prefetchable, where a 32 KB stride is a stride the prefetcher can
recognize but cannot help with, because every line it fetches is evicted
before reuse.

This is the one transformation with no trade-off to weigh. No work removed, no
precision traded, no parameter to tune — only a legality question.

### The reasoning trap worth internalizing

The tempting argument is: the inner loop touches one row of A (32 KB) plus all
of `x` (32 KB), so the working set is 64 KB — against a 48 KB L1, that does
not fit, and the optimization should not work.

It works fine. The row of A is read once, in order, and never revisited; it
*streams*, and retaining it would buy nothing. Only `x` is re-read for every
row, so only `x` has to stay resident — 32 KB against 48 KB, comfortably.

> **Count what must be retained, not what is touched.**

## 4 · Fission — the one where you can see the mechanism

Thirty-two simultaneous cross-correlations in one loop body needs 32
accumulators plus 32 reference pointers, against x86-64's 16 XMM and 16
general-purpose registers. The compiler spills, and pays a load and a store
per spilled value per iteration. Splitting the loop reduces the live set.

What makes this the cleanest example in the directory is that the mechanism is
*countable*. From the generated assembly:

| accumulators per loop | loops | time | speedup | stack refs |
|---:|---:|---:|---:|---:|
| 32 | 1 | 237.9 ms | 1.00x | **134** |
| 16 | 2 | 92.0 ms | 2.59x | **57** |
| **8** | **4** | **55.6 ms** | **4.28x** | **0** |
| 4 | 8 | 53.1 ms | 4.48x | 0 |

> **Show in class:**
> [loop_fission_spill.html](../examples/loop_optimizations/loop_fission_spill.html)
> — the two register banks drawn as slots, with the overflow dropping into the
> stack as you widen the loop body. Nothing spills at 8 accumulators, which is
> where the curve above bends. Double-click to open; no server needed.

The speedup is not a plausible story about caches — it is the elimination of a
counted number of instructions, and the curve bends exactly where the count
reaches zero. `grep -c '(%rsp)'` turns the whole question into an observation.

Two lessons:

**The natural split is the wrong one.** Splitting 32 in half leaves 57 stack
references and most of the win unclaimed. On an ISA with 32 FP registers, 16
per loop would fit. **The right fission width is a property of the register
file, not of the algorithm** — re-measure it whenever you change targets.

**Write the accumulators as local variables.** If you accumulate directly into
the output array, the compiler cannot prove `c[k]` does not alias the input,
so it reloads from memory every iteration and never uses registers at all. You
get a slow loop with *zero* spills — the same symptom, a different disease,
and a profile that points nowhere. This is the aliasing story from Lecture 04
showing up in a new place.

## 5 · Tiling — and the question to ask before you use it

Tiling blocks the iteration space so that a working set fits in a fast cache
level. Whether that helps depends entirely on one property of the kernel:
**how many times it reads the same byte.**

```
reuse factor = work / data
```

Matrix multiply does O(N³) work on O(N²) data, so every element of B is read N
times and blocking turns those re-reads into cache hits. A transpose does O(N²)
work on O(N²) data — **each element is read exactly once**. There is no temporal
reuse for a tile to capture at all.

We will do both, because they give opposite answers and the contrast is the
lesson.

### The no-reuse case: transpose

Transposing a 4096×4096 matrix. Naive is 188 ms; tiled at B=16 is 34 ms, a
**5.5x** speedup. Textbook result, and real.

Now the uncomfortable part. Change nothing about the loop; change the row
stride from 4096 to 4104 doubles. The *naive* transpose drops to **24 ms —
7.8x faster, and 1.4x faster than the best tile size ever achieves.** After
that, tiling is a net loss.

### Why

A line's L1 set here is `(address / 64) % 64` — the associativity result from
[Lecture 05](05.memoryhierarchy.md#3--processor-caching-concepts), now with a
loop attached. Walking down a column steps one
row — `lda × 8` bytes, or `lda/8` lines — so the set index advances by
`(lda/8) % 64` per step, and a column reaches

```
sets_reachable = 64 / gcd((lda/8) % 64, 64)
```

distinct sets. At `lda = 4096` that advance is **0**: every element of a
column lands in *one* set, which has 12 ways. A 4096-element column evicts
itself continuously. That, and not the tile size, is why the naive transpose
cost 188 ms.

Sweeping the leading dimension makes the whole effect visible: the naive time
tracks `sets_reachable` monotonically and collapses once a column reaches 16
sets — because 16 sets × 12 ways is enough to hold the column. The same
threshold shows up in `set_conflict.c` in the memory-hierarchy examples,
reached with a completely different kernel.

### The rules that do not work

* **Capacity**, `2B²·8 ≤ 48 KB`, predicts `B ≤ 55`. Badly wrong — B=48 and
  B=64 are near the bottom of the sweep.
* **`B ≤ associativity`** predicts 12, lands in the right neighbourhood, and
  still does not pick the measured optimum of 16. It also varies by machine,
  so it does not transfer.
* **"Avoid powers of two"** is not the rule either. `lda = 4352` is not a
  power of two and is still 3.1x off the best; `lda = 4097` is odd and
  performs like the well-padded cases. The rule is *how many factors of two
  the row length contains when measured in cache lines* — which is what the
  `gcd` counts.

The sweep is not even smooth: **B=10 is reproducibly worse than B=8**, because
8 doubles is exactly one 64-byte line and 10 straddles two. If you need a tile
size, sweep for it; do not derive it.

> **With no reuse to capture, pad the leading dimension first, and reach for
> tiling only if it still does not fit.** This is why BLAS and NumPy pad array
> dimensions.

### The reuse case: matrix multiply

Now the other kernel. Baseline is `i,k,j` — interchange already applied — so
everything here is what *blocking* buys on top of the best loop order. `-O3`,
tile size 256:

| n | total | i,k,j | + block j | + block i,j,k |
|---|---|---:|---:|---:|
| 512 | 6 MB — fits L3 | 27.2 GF/s | 29.5 | **34.5** (1.27x) |
| 1024 | 24 MB | 26.5 GF/s | 22.8 | **31.9** (1.20x) |
| 2048 | 96 MB | 10.7 GF/s | 22.0 | **31.8** (2.98x) |

Read the blocked column down the page: ~32 GF/s at every size. It is
compute-bound, and the problem size has stopped mattering. The baseline holds up
while the matrices fit in L3 and collapses when they do not — at n=2048 it
re-reads all 32 MB of B once per row of A, roughly 69 GB of traffic against a
~39 GB/s DRAM ceiling.

So here tiling is not a constant-factor tweak. It changes the algorithm's memory
traffic from O(N³) to O(N³/T), and the win **grows** with the problem.

The two effects are also independent. Padding the leading dimension helps the
*blocked* version at small tile sizes and does nothing at all for the unblocked
one, while blocking wins ~3x with or without it. **Tiling buys reuse; padding
buys conflict-freedom.** They compose, and neither substitutes for the other.

> **A trap worth carrying out of this.** That entire table is `-O3`. At `-O2`,
> GCC's `very-cheap` vectoriser cost model refuses the inner loop, every version
> runs scalar at ~1.3 flops/cycle, the kernel becomes memory-bound, and blocking
> measures within 4% of not blocking — the experiment says tiling is worthless.
> One flag inverts the conclusion. Check that your kernel vectorised before
> concluding anything about memory.

## How to take a measurement you can trust

This directory is also the best demonstration in the course of how a benchmark
lies to you. Three traps, all of which produce *stable, reproducible* wrong
answers — which is what makes them dangerous.

**1. Heterogeneous cores.** This chip has four Zen 5 cores at 5.13 GHz and
eight Zen 5c "dense" cores at 3.17 GHz. An unpinned run lands wherever the
scheduler puts it: a 1.6x spread from the same binary. Pin your benchmark.

**2. The governor boosts on IPC, not on being busy.** `amd-pstate-epp` in its
default mode raises the clock in response to instructions-per-cycle. A
memory-bound loop has *low* IPC and never triggers a boost, so it runs the
whole way at ~3.59 GHz. Measured on the transpose: **263 ms on all eight
repetitions cold, 184 ms on all eight after a warm-up spin** — a 1.43x error.

Note what defeats the obvious defence. Taking the minimum of five runs does
not help, because every run is equally slow. The wrong number is perfectly
repeatable. The fix is to spin on a *high-IPC* loop first — and note that
spinning on a dependent chain does not work, because that loop is itself
low-IPC.

**3. The compiler deletes the work.** Call the same pure function on the same
data in a timing loop and it is loop-invariant; the compiler is entitled to
hoist it out and run it once. The benchmark then reports `0.0 ms`, which is at
least a conspicuous way to fail. Perturb the input each repetition.

All three are handled in the sources, and each program prints the clock it
actually measured at, at both ends of the run, so a drifting clock is visible
rather than silent.

> A speedup *ratio* survives traps 1 and 2; the absolute times do not. That is
> a reason to report both — a ratio that holds while the absolutes move is
> evidence you are looking at a real effect.

## The through-line

Five transformations, and every textbook rule for applying them failed at
least partly on contact with this machine:

* Unrolling removes overhead that an out-of-order core had already made free.
* The fission width is set by the register file, not the algorithm.
* Neither tiling rule picks the tile, and on a kernel with no reuse the
  padding beats the tiling outright.
* The interchange working-set argument overcounts unless you separate
  streamed data from retained data.

What survived is not a rule but a habit. **Name the resource the loop is short
of — issue slots, memory passes, cache lines, registers, cache sets — and pick
the transformation that relieves that one.** Then measure, because the
parameter the formula gives you and the parameter that wins are usually not
the same number.

That habit is also the bridge to the rest of the course. Three of these five
were limited by the memory system rather than by the processor, and we have
been characterizing that memory system by analogy. Next we measure it
directly.
